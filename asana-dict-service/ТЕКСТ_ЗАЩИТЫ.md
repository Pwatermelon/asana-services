## СЛАЙД 3: Проблема и актуальность

Прежде чем перейти к описанию решения, хочу остановиться на проблемах, которые существуют в предметной области.

Анализ существующих веб-ресурсов, посвященных асанам йоги, выявил ряд характерных проблем. **Во-первых**, большинство ресурсов используют собственную систему классификации асан, которая может не совпадать с классификациями других источников, что создает путаницу и затрудняет сравнение информации.

**Во-вторых**, информация об асанах часто представлена без указания источника, что снижает достоверность данных и затрудняет верификацию.

**В-третьих**, разные ресурсы используют различные системы названий — русские, санскрит, транслитерация, что усложняет поиск и сопоставление информации.

И **наконец**, информация разрознена по множеству ресурсов, что затрудняет получение полной картины об асане.

В рамках предыдущей курсовой работы была разработана онтологическая модель, которая решает эти проблемы. **Ключевое решение** заключается в привязке каждой асаны к конкретному источнику, что позволяет избежать субъективности и обеспечивает возможность корректного представления различных трактовок одной и той же позы в разных школах и публикациях.

Онтология разработана на языке OWL и обеспечивает формализацию знаний для интеграции с другими семантическими системами.

## СЛАЙД 4: Архитектура системы

Теперь перейду к описанию архитектуры разработанной системы.

Разрабатываемая система построена по принципу **микросервисной архитектуры** и состоит из нескольких основных компонентов.

На клиентском уровне пользователь взаимодействует с системой через браузер. Все запросы проходят через **Nginx**, который выступает в роли reverse proxy и маршрутизирует запросы к соответствующим сервисам.

**Frontend-сервис** реализован на React с использованием Vite в качестве инструмента сборки. Он предоставляет пользовательский интерфейс и взаимодействует с backend через REST API.

**Backend-сервис** разработан на FastAPI и обеспечивает всю бизнес-логику системы. При необходимости он проверяет авторизацию через внешний сервис авторизации — **server-module**.

Для хранения данных используется несколько хранилищ:
- **PostgreSQL** — для служебных данных, таких как пользователи, записи модерации и настройки системы
- **OWL-онтология** — для предметных данных об асанах, источниках и фотографиях
- **MinIO S3** — объектное хранилище для файлов и изображений

Такая архитектура обеспечивает **независимое развитие компонентов**, **горизонтальное масштабирование** и **отказоустойчивость**. Каждый сервис может разрабатываться и развертываться независимо, что упрощает поддержку и развитие системы.

## СЛАЙД 5: Технологический стек

Для реализации системы был выбран современный технологический стек.

**Backend** построен на **FastAPI** — асинхронном веб-фреймворке, который обеспечивает высокую производительность и автоматическую генерацию документации API. Для работы с базой данных используется **SQLAlchemy** как ORM, что обеспечивает безопасность от SQL-инъекций и абстракцию от СУБД.

Для работы с OWL-онтологией используется библиотека **rdflib**, которая позволяет загружать онтологию, выполнять SPARQL-запросы и модифицировать данные.

Для импорта и экспорта данных из Excel используется библиотека **openpyxl**, а для работы с объектным хранилищем — **MinIO Python Client**.

**Frontend** реализован на **React 18** с использованием компонентной архитектуры. Для маршрутизации используется **React Router**, а для сборки — **Vite**, который обеспечивает быструю разработку с hot module replacement.

**Инфраструктура** полностью контейнеризована с помощью **Docker** и **Docker Compose**. Все сервисы упакованы в контейнеры, что обеспечивает простоту развертывания и воспроизводимость окружения.

## СЛАЙД 6: Онтологическая модель

Теперь остановлюсь подробнее на онтологической модели предметной области.

Онтология включает несколько основных классов. **AsanaSource** — это класс источника с метаданными: название, автор, год издания, издательство и аннотация.

**AsanaName** — класс для вариантов названий асаны, включающий название на русском языке, санскрит, транслитерацию и определение.

**Asana** — это класс асаны в контексте конкретного источника. Каждая асана связана с одним источником через свойство hasSource и с одним названием через hasName.

**AsanaPhoto** — класс фотографии асаны, который содержит путь к файлу в S3, хеш фотографии для проверки дубликатов и связь с источником.

**SameAsObject** — класс для связи похожих асан, что позволяет группировать различные трактовки одной позы из разных источников.

**Ключевой принцип моделирования** заключается в том, что асана определяется не абстрактно, а в контексте конкретного источника и варианта названия. Это позволяет избежать субъективности и неоднозначности, а также обеспечивает возможность корректного представления различных трактовок одной и той же позы в разных школах и публикациях.

Такая структура обеспечивает расширяемость системы, возможность интеграции с внешними базами знаний и корректное отображение многообразия подходов в йоге.

## СЛАЙД 7: Основные модули системы

Система состоит из пяти основных модулей, которые взаимодействуют друг с другом.

**Модуль авторизации** обеспечивает интеграцию с внешним сервисом авторизации. При каждом запросе backend отправляет JWT-токен в server-module для проверки валидности и получения информации о пользователе.

**Модуль работы с онтологией** инкапсулирует всю логику работы с OWL-онтологией. Он предоставляет высокоуровневый API для операций CRUD с асанами, источниками и фотографиями, скрывая детали работы с RDF и SPARQL.

**Модуль импорта и экспорта** интегрирует функциональность работы с Excel-файлами. Он поддерживает импорт асан вместе с изображениями, автоматическое создание источников при импорте и экспорт записей модерации.

**Модуль модерации** обеспечивает контроль качества импортируемых данных. При обнаружении похожих названий система автоматически сохраняет записи на модерацию, которые затем проверяются экспертами.

**Модуль работы с файлами** отвечает за загрузку фотографий в MinIO S3, проверку дубликатов по хешу и получение файлов через presigned URL.

Все модули тесно интегрированы и обеспечивают единый рабочий процесс для пользователей системы.

## СЛАЙД 8: Интеграции с внешними сервисами

Теперь опишу схему взаимодействия системы с внешними сервисами.

Когда пользователь делает запрос через frontend, запрос маршрутизируется через Nginx к backend-сервису. Backend извлекает JWT-токен из заголовка запроса и отправляет его в сервис авторизации для проверки.

Сервис авторизации проверяет токен и возвращает данные о пользователе, включая его роль. На основе этих данных backend определяет права доступа к запрашиваемому ресурсу.

Для получения служебных данных backend обращается к PostgreSQL, используя схему dict_schema для изоляции данных от других сервисов.

Для работы с предметными данными backend выполняет SPARQL-запросы к онтологии, которая загружена в память при старте приложения.

Если запрос требует работы с файлами, backend взаимодействует с MinIO S3 для загрузки или получения файлов.

**Особенности интеграции:**
- Централизованная авторизация через server-module упрощает управление пользователями
- Общая база данных PostgreSQL с изоляцией через схемы упрощает управление инфраструктурой
- S3-совместимое хранилище обеспечивает масштабируемость и возможность миграции на облачные хранилища

## СЛАЙД 9: Система модерации

Одной из ключевых особенностей системы является механизм модерации импортируемых данных.

Процесс начинается с загрузки Excel-файла пользователем. Система парсит файл, извлекая данные об асанах, источниках и изображениях.

При обработке данных система использует нечеткий поиск для проверки наличия похожих названий в онтологии. Если найдены похожие названия, система автоматически сохраняет запись на модерацию с указанием типа проблемы.

Эксперт может просмотреть записи на модерацию и разрешить конфликт одним из способов:
- Выбрать существующую асану и привязать к ней данные
- Создать новую асану из данных модерации
- Экспортировать запись в Excel для исправления и повторного импорта

После разрешения конфликта данные загружаются в онтологию.

**Типы модерации:**
- **error** — ошибки при импорте, такие как некорректные данные
- **name_mismatch** — несоответствие названий при высокой схожести
- **duplicate_name** — обнаружение дубликатов названий
- **duplicate_source** — обнаружение дубликатов источников

Такая система обеспечивает контроль качества данных и предотвращает появление дубликатов и некорректной информации в онтологии.

## СЛАЙД 11: Безопасность системы

Безопасность системы обеспечивается на нескольких уровнях.

**Аутентификация** реализована через JWT-токены, которые проверяются через внешний сервис авторизации. Токены хранятся в HttpOnly cookies для защиты от XSS-атак.

**Авторизация** основана на системе ролей: администратор, эксперт и пользователь. Каждая роль имеет определенные права доступа, которые проверяются как на уровне API, так и на уровне frontend через защищенные маршруты.

**Валидация данных** осуществляется с помощью Pydantic моделей на backend и проверки на frontend. Все входные данные проверяются на типы, форматы и ограничения.

**Защита от атак** включает:
- CSRF-защиту через SameSite cookies и проверку origin запросов
- XSS-защиту через автоматическое экранирование данных в React
- Защиту от SQL-инъекций через использование ORM SQLAlchemy

**Работа с файлами** включает проверку MIME-типов, ограничение размеров файлов и проверку дубликатов по хешу перед загрузкой.

## ВОЗМОЖНЫЕ ВОПРОСЫ И ОТВЕТЫ

### Вопрос 1: Почему была выбрана микросервисная архитектура, а не монолитная?

**Ответ:** Микросервисная архитектура была выбрана по нескольким причинам. Во-первых, система разрабатывается в контексте существующей инфраструктуры, где уже есть сервис авторизации и общая база данных. Микросервисная архитектура позволяет интегрироваться с этими компонентами без дублирования функциональности.

Во-вторых, микросервисная архитектура обеспечивает независимое развитие компонентов. Например, frontend и backend могут разрабатываться разными командами и развертываться независимо.

В-третьих, такая архитектура обеспечивает горизонтальное масштабирование. Если нагрузка на backend увеличится, можно запустить несколько экземпляров backend-сервиса за балансировщиком нагрузки.

И наконец, микросервисная архитектура обеспечивает отказоустойчивость. Если один сервис недоступен, остальные продолжают работать.

### Вопрос 2: Как работает интеграция с онтологией? Почему не используется только реляционная база данных?

**Ответ:** Интеграция с онтологией реализована через библиотеку rdflib. При старте приложения онтология загружается из файла в объект Graph, который представляет собой набор RDF-триплетов.

Для поиска и извлечения данных используются SPARQL-запросы — стандартный язык запросов для RDF-данных. SPARQL позволяет формулировать сложные запросы с фильтрацией, объединениями и агрегацией.

При модификации данных создаются или удаляются соответствующие RDF-триплеты в графе, и все изменения сохраняются обратно в файл онтологии.

Почему не только реляционная база данных? Онтологический подход имеет несколько преимуществ. Во-первых, он обеспечивает формализацию знаний в стандартном формате OWL, что позволяет интегрироваться с другими семантическими системами. Во-вторых, онтология позволяет гибко расширять структуру данных без необходимости миграций базы данных. В-третьих, онтологический подход решает проблему субъективности данных через привязку каждой асаны к конкретному источнику.

Реляционная база данных используется для служебных данных — пользователи, модерация, настройки, которые не требуют семантического моделирования.

### Вопрос 3: Как обеспечивается безопасность системы?

**Ответ:** Безопасность обеспечивается на нескольких уровнях.

**Аутентификация:** Все запросы, требующие авторизации, проверяются через внешний сервис авторизации. JWT-токены содержат информацию о пользователе и его роли, подписанную секретным ключом. Токены хранятся в HttpOnly cookies для защиты от XSS-атак.

**Авторизация:** На уровне API операции защищены декораторами, которые проверяют роль пользователя. Например, декоратор `is_admin` разрешает доступ только администраторам, а `is_expert_or_admin` — экспертам и администраторам. На уровне frontend защищенные маршруты проверяют права доступа перед отображением страницы.

**Валидация данных:** Все входные данные валидируются с помощью Pydantic моделей на backend и проверяются на frontend. Это предотвращает передачу некорректных данных и защищает от инъекций.

**Защита от атак:** CSRF-защита обеспечивается использованием SameSite cookies и проверкой origin запросов. XSS-защита реализуется автоматическим экранированием данных в React. Защита от SQL-инъекций обеспечивается использованием ORM SQLAlchemy вместо прямых SQL-запросов.

**Работа с файлами:** При загрузке файлов проверяется MIME-тип и расширение, разрешаются только изображения в определенных форматах. Установлены ограничения на размер файлов. Перед загрузкой вычисляется хеш файла для проверки дубликатов.

### Вопрос 4: Как работает система модерации? Что происходит при обнаружении конфликтов?

**Ответ:** Система модерации обеспечивает контроль качества импортируемых данных.

При импорте данных из Excel система выполняет несколько проверок. Во-первых, для каждого названия асаны выполняется нечеткий поиск в онтологии с использованием библиотеки rapidfuzz. Если найдены похожие названия с высоким коэффициентом схожести, система сохраняет запись на модерацию.

Типы модерации включают:
- **error** — ошибки при импорте, такие как некорректные данные или отсутствие обязательных полей
- **name_mismatch** — несоответствие названий при обнаружении похожих названий
- **duplicate_name** — обнаружение дубликатов названий в импортируемых данных
- **duplicate_source** — обнаружение дубликатов источников

Данные импорта сохраняются в JSON-формате в базе данных вместе с информацией о типе проблемы и связанных асанах или источниках.

Эксперт может просмотреть записи на модерацию через специальный интерфейс. При разрешении конфликта эксперт может:
- Выбрать существующую асану и привязать к ней данные из модерации
- Создать новую асану из данных модерации
- Экспортировать запись в Excel для исправления и повторного импорта
- Отметить запись как решенную, если проблема была устранена другим способом

После разрешения конфликта данные загружаются в онтологию, и запись модерации помечается как решенная.

### Вопрос 5: Какие были основные трудности при разработке и как они решались?

**Ответ:** Основные трудности были связаны с несколькими аспектами.

**Первая трудность** — работа с OWL-онтологией. Изначально не было опыта работы с RDF и SPARQL. Решение: изучение документации библиотеки rdflib, практика написания SPARQL-запросов и создание высокоуровневого API, который скрывает сложность работы с RDF.

**Вторая трудность** — интеграция с внешним сервисом авторизации. Нужно было обеспечить корректную проверку токенов и обработку ошибок при недоступности сервиса. Решение: реализация асинхронных HTTP-запросов через httpx, обработка таймаутов и graceful degradation при недоступности сервиса.

**Третья трудность** — импорт данных из Excel с изображениями. Нужно было извлекать изображения из ячеек Excel, декодировать их и загружать в S3. Решение: использование библиотеки openpyxl для работы с изображениями в Excel, создание функции для извлечения и декодирования base64-изображений.

**Четвертая трудность** — обеспечение производительности при работе с большими объемами данных. При загрузке больших Excel-файлов система могла зависать. Решение: реализация фоновой обработки больших файлов с отображением прогресса пользователю.
